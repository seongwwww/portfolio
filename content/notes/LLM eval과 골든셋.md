# LLM eval과 골든셋

> LLM을 쓰는 순간 "잘 되는 것 같다"는 근거가 될 수 없다. 채점표를 먼저 만든다.

## [[실은 silen]] — eval을 완료 조건에 넣었다

**"완료(Definition of Done) = lint + typecheck + unit + integration + eval 전부 통과."**

`evals/` 아래 3종 스위트. 각각 `fixtures.json` + `run.py`:

| 스위트 | 검증 대상 |
|---|---|
| `diary` | 일기 생성 |
| `entities` | 엔티티 추출 |
| `narration` | 차이 서술 |

### 측정 지표 5종
환각율 · 조언혼입율 · 톤불변성 통과율 · 근거정합율 · false positive율

### 골든셋 규칙
- eval 골든셋을 **1일차부터** 유지
- **골든셋 통과가 CI 게이트**
- 프롬프트·detector·모델 변경 시 eval 자동 실행
- 필수 케이스: 빈 날(억지 생성 X) · 미세 이탈 · 환각 유혹 · 감정 승격 · 톤 불변성 · 근거 정합 · 상관≠인과
- **"평범한 날을 억지로 특별하게 만들지 않는" 테스트를 반드시 포함**

## [[정책핏 인천]] — 정답셋이 틀렸다는 걸 발견했다

정답셋을 16건 → 31건으로 늘렸는데(D-017), **판별력 결함**이 있었다. 쉬운 케이스만 있어서 뭘 넣어도 통과하는 정답셋이었다.

양성 통제군을 추가하고 프롬프트를 v7까지 밀었다 — **지표가 나빠지는 방향의 갱신**(D-018).

> 자기 점수를 깎는 쪽으로 평가 기준을 고친 결정. 이 프로젝트에서 가장 자랑할 만한 판단이다.

자체 루브릭도 직접 만들어 **70 → 76 → 77**로 스스로 채점하며 개선했다.
